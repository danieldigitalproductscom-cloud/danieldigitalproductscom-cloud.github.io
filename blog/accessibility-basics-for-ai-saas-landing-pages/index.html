Accessibility Basics Every AI/SaaS Landing Page Needs (and What It Costs to Skip Them)

Accessibility gets treated as a legal checkbox founders mean to get to "after launch," which usually means never. That's a mistake on two fronts: a meaningful share of visitors — people using screen readers, keyboard-only navigation, or a browser zoomed to 200% — simply bounce off an inaccessible page without ever telling you why, and accessibility complaints against SaaS marketing sites have become common enough that ignoring them is a real legal exposure, not a hypothetical one. None of the fixes below require a framework or a redesign. Here's what actually matters, in the order it's cheapest to fix.

1. Color contrast: check it, don't eyeball it

WCAG AA requires a 4.5:1 contrast ratio for normal text and 3:1 for large text (18px+ bold or 24px+ regular) and UI components like button borders. The most common failure on AI/SaaS pages is a light accent color — the violets, cyans, and pastels that read as "modern" — used as text on a white or near-white background, or white text on a mid-tone accent button. Run every text/background pairing through WebAIM's contrast checker before you ship, not after a complaint. If a brand color fails, don't abandon it: darken it a few shades for text use and keep the lighter version for decorative accents where legibility doesn't matter.

2. Keyboard navigation: tab through your own page once

Every interactive element — nav links, the pricing toggle, FAQ accordions, the CTA button — needs to be reachable and operable using only the Tab and Enter keys, in an order that matches the visual layout. The single most common violation is removing the default focus outline with outline: none for aesthetics and never replacing it, which leaves keyboard users with no way to see where they are on the page. If you don't like the default outline, style a custom one with :focus-visible — don't remove it outright. Do a full keyboard-only pass on your own page before launch; it takes three minutes and catches this instantly.

3. Respect prefers-reduced-motion

Scroll-reveal animations and parallax effects are common on modern landing pages, and for a meaningful number of visitors with vestibular disorders, that motion causes real discomfort, not just mild annoyance. Wrap animation rules in a media query and disable or drastically simplify them when the user has requested it:

@media (prefers-reduced-motion: reduce) {
  * { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; }
}

This is a five-minute addition to a stylesheet, and it costs nothing for the visitors who don't have the preference set — the animation runs exactly as designed for everyone else.

4. One H1, a real heading hierarchy, and landmark regions

Screen reader users frequently navigate a page by jumping between headings, not by reading top to bottom — which means a page with three H1s, a skipped H3, or "features" and "pricing" both marked as generic <div>s is far harder to scan than one with a clean H1 → H2 → H3 structure. Wrap the page in real landmark elements too: <nav>, <main>, <footer>. These cost nothing visually — they're a markup choice, not a design choice — but they're the difference between a screen reader user skimming your page in ten seconds and giving up on it.

5. Label every form field, not just the placeholder

A placeholder that disappears the moment someone starts typing is not a label — screen readers may not announce it consistently, and sighted users lose the field's purpose the moment they start filling it in. Every input needs a real <label> element (visually hidden if your design calls for it) tied to the input via a matching for/id pair. Error messages need the same treatment: associate them with aria-describedby so a screen reader announces "email — invalid format" instead of leaving the user to guess which field the red text below the form refers to.

6. Alt text that describes, decorative images that don't need it

An image that conveys real information — a screenshot of the product, a chart, a diagram — needs alt text that describes what it shows, not the filename ("hero-image-final-v2.png" tells a screen reader user nothing). An image that's purely decorative — a background texture, a gradient blob — should have alt="" so screen readers skip it entirely instead of announcing something meaningless and wasting the listener's time. Getting this backwards in either direction is worse than doing nothing: describing decoration is noise, and leaving real content undescribed is a gap.

7. Build accordions and toggles out of real buttons

An FAQ accordion or pricing toggle built from a <div onclick=""> is invisible to keyboard and screen reader users — it has no focus state, no announced role, and no way to activate it without a mouse. Use a real <button> element with aria-expanded="true/false" reflecting its current state. This is a small markup change that makes the same visual component fully operable for everyone, with no design compromise.

The pattern underneath all of this

Every fix here replaces something a visitor has to guess at — where the focus is, what a field is for, whether an image matters — with something they can perceive directly, which is exactly the same principle that makes a comparison table or a pricing page trustworthy. Accessibility isn't a separate audience to design for after the "real" page is done; a page built with real semantic HTML, labeled forms, and visible focus states is very often just a better-built page for every visitor, screen reader or not.

If you're building a page for a category where trust and fairness are already part of the pitch — hiring, HR, finance — getting the accessibility basics right on your own landing page is a quiet but real credibility signal before a visitor has read a word of copy.
