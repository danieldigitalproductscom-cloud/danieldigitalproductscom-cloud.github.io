Client-Side vs. Server-Side Rendering: Why AI SaaS Landing Pages Go Invisible to Crawlers

A founder ships a landing page built with their app's React stack, because it's the tool already open on their laptop. It looks flawless in the browser. Then three months later, organic traffic is flat, ChatGPT and Perplexity never mention the product even when asked directly about the category, and Search Console shows the page indexed with a title and nothing else. The page isn't broken — it's invisible. Here's why that happens and exactly how to fix it.

1. What "client-side rendered" actually means for a crawler

When a browser requests a client-side rendered (CSR) page, the server sends back a nearly empty HTML shell — a <div id="root"></div> and a bundle of JavaScript. The browser then runs that JavaScript to build the actual page in the DOM. A human never notices this happens in milliseconds. But a crawler that only fetches HTML — which is still most of them — sees the empty shell and stops there. It never runs your JavaScript, so as far as it's concerned, your headline, your pricing table, and your FAQ don't exist.

2. Googlebot is the exception, not the rule

Google's crawler does execute JavaScript, using a headless Chromium renderer — but it does so in a second, deferred pass that can lag the initial crawl by days, and it runs on a finite "render budget" per site. Bing's crawler renders JavaScript far less reliably. And the crawlers that matter most for 2026's traffic mix — GPTBot, ClaudeBot, PerplexityBot, and the other AI answer-engine crawlers — largely do not execute JavaScript at all. They fetch raw HTML and read what's there. If your content only exists after a script runs, these crawlers see nothing, and your product simply can't be cited in an AI-generated answer no matter how good it is.

3. Check this in five minutes, not with an audit tool

You don't need a paid crawler to find out if you have this problem. Run curl -A "Mozilla/5.0" https://yoursite.com | less and read the raw HTML that comes back. If your headline, body copy, and pricing text are sitting there in plain text, you're fine. If you see a near-empty shell and a pile of <script> tags, that's exactly what every non-JS-executing crawler sees too. A faster check: open your page, disable JavaScript in DevTools, and hard-refresh. Whatever's still on screen is what most AI crawlers can read.

4. Server-side rendering and static generation both fix this — pick based on your stack

The fix isn't to abandon your framework, it's to make sure the HTML that leaves your server already contains the content. You have two solid options. Server-side rendering (SSR) — Next.js, Nuxt, SvelteKit's server mode — renders the page to HTML on each request, so the first response already has real content, and the JavaScript then "hydrates" it for interactivity. Static site generation (SSG) — Astro, Eleventy, Next.js's static export, or even a prerendering step that runs a headless browser at build time and saves the output as plain HTML files — goes further and produces the finished HTML once, ahead of time, which is also faster and cheaper to serve. For a marketing landing page specifically, SSG is almost always the better call: the content doesn't change per-visitor, so there's no reason to pay a render cost on every request.

5. The common half-fix: SSR the app shell, hide the content anyway

Teams sometimes "fix" this by switching their framework to SSR mode, then still lose the content because of a second, subtler issue: data that's fetched client-side after the initial render. If your pricing table, testimonials, or FAQ answers are populated by a useEffect or a client-side API call that fires after mount, the server still ships an empty container for that section — SSR only rendered the shell around it. Anything a crawler needs to see has to be present in the HTML the server sends on the very first response, not fetched afterward. Audit each section of your page and ask specifically: is this text present in the raw HTML, or does something have to run first to produce it?

6. Accordions, tabs, and "click to expand" FAQs have the same failure mode

Even on a properly server-rendered page, a common pattern quietly defeats the purpose: FAQ answers or feature descriptions that only exist in the DOM once a user clicks to expand them, built with JavaScript that injects the content on interaction rather than CSS that just hides it. If the answer text isn't in the HTML at all until a click fires, it doesn't matter that the rest of the page rendered server-side — that content is still invisible to a crawler that never clicks anything. Use a native <details>/<summary> element or CSS-only show/hide so the text ships in the HTML and is simply visually collapsed, not absent.

7. Keep the app SPA, make the marketing site static

You don't have to rebuild your product dashboard's rendering strategy to fix this — the dashboard sits behind a login wall no crawler will ever reach anyway. The fix only needs to apply to the public-facing marketing site: the homepage, pricing, and any content pages. It's common and entirely reasonable to run your authenticated app as a pure client-side SPA for speed and simplicity, while building the marketing site as a separate static or server-rendered project, even on a different framework, that ships at yoursite.com while the app lives at app.yoursite.com.

The five-minute audit

  • Curl your homepage with a plain user agent and check whether your headline and body copy are in the raw response.
  • Disable JavaScript in your browser and reload every marketing page — pricing, FAQ, comparison pages — to see what survives.
  • Search Console → URL Inspection → "View Crawled Page" to see exactly what Google's renderer captured, not what you assume it captured.
  • Grep your codebase for FAQ or pricing content gated behind a useEffect, a click handler, or a client-only fetch, and move it into the initial server-rendered payload.

None of this requires a rewrite. It requires making sure the words you already wrote are actually sitting in the HTML your server sends out — before any JavaScript runs, for every visitor that will never run it, human or otherwise.
