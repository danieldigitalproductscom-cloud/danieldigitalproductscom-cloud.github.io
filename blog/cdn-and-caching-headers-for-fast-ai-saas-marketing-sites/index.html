CDN and Caching Headers for Fast AI SaaS Marketing Sites

Most AI/SaaS marketing sites are mostly static: a home page, pricing, feature pages and a blog. Yet many are served from a single origin region with no caching, so a visitor in Singapore waits for a server in Virginia on every request. A CDN and correct caching headers are the cheapest speed upgrade available, and faster Time to First Byte helps Largest Contentful Paint, conversion and crawl efficiency. Here is how to do it without serving stale or wrong pages.

1. Separate your marketing site from your app

Your logged-in product is dynamic and personalized; your marketing pages are not. Serve them from different paths or hosts (for example example.com for marketing and app.example.com for the product) so you can cache aggressively on one and never on the other. Mixing them is how private data ends up cached and shown to the wrong visitor.

2. Put a CDN in front of the origin

Static hosts such as Cloudflare Pages, Netlify, Vercel or a CDN like Cloudflare, Fastly or CloudFront in front of your own server all do the same job: keep copies of your pages at edge locations near visitors. For a static or pre-rendered site, serve the whole HTML document from the edge. Check the result by requesting a page twice and looking for a cache-status response header (names vary: cf-cache-status, x-cache, x-vercel-cache). The second request should say HIT.

3. Cache fingerprinted assets for a year

CSS, JavaScript, fonts and images whose filenames contain a content hash (such as app.3f9a1c.css) never change at a given URL, so cache them forever:

Cache-Control: public, max-age=31536000, immutable

The immutable directive tells browsers not to revalidate on reload. This only works if your build really fingerprints filenames. If you serve style.css with a one-year lifetime and then edit it, returning visitors keep the old file.

4. Treat HTML differently

HTML references those hashed assets, so it must update quickly after a deploy. Two safe patterns:

  • Short browser cache, longer edge cache: Cache-Control: public, max-age=0, s-maxage=600, stale-while-revalidate=86400. Browsers revalidate each time; the CDN serves a copy for ten minutes and refreshes in the background.
  • Long edge cache with purge on deploy: cache HTML at the edge for a day or more and have your deploy pipeline purge the cache. Most CDNs offer a purge API; wire it into CI so a release can never leave stale pages up.

Avoid max-age of hours on HTML in the browser. You cannot recall a copy that is already sitting in someone's browser, and a stale pricing page is an expensive bug.

5. Use validators so revalidation is cheap

When a cache revalidates, a response with an ETag or Last-Modified header lets the origin answer 304 Not Modified with no body. Most static hosts add these automatically. If you run your own server, confirm that compression and ETags are on, and serve Brotli for text assets.

6. Be careful with cookies and query strings

Two common causes of mysteriously low hit rates:

  • Set-Cookie on marketing pages. Many CDNs refuse to cache responses that set cookies. Do not set session or analytics cookies from the origin on public pages; load analytics client-side.
  • Query strings in the cache key. Campaign URLs with utm_source, gclid and similar parameters can each become a separate cache entry. Configure the CDN to ignore tracking parameters in the cache key, while keeping them intact for client-side analytics.

Also make sure the canonical tag on parameterized URLs points to the clean URL, as covered in our canonical tag guide.

7. Never cache what is personal or error states

Pages that depend on the visitor, such as a signed-in dashboard, checkout or a geo-personalized price, should return Cache-Control: private, no-store or vary correctly. If you localize by country, either use separate URLs per locale (best for SEO) or include the relevant header in Vary. Do not cache 5xx responses for long; a one-minute error cache prevents hammering a failing origin, but an hour-long one turns a blip into an outage. Likewise, do not let a CDN cache a soft 404 as a normal page.

8. Keep crawlers and bots in mind

Googlebot benefits from fast responses; a CDN lowers server time per request, so Google can crawl more URLs in the same budget. But bot-protection rules can backfire: challenge pages or aggressive rate limits served to crawlers look like errors. Allow verified search crawlers, and check your server logs or the Crawl Stats report in Search Console for spikes in 403, 429 or 5xx responses after you enable a CDN or firewall rule.

9. Preload and connect early

Caching removes distance; resource hints remove waiting. Preload the hero image and the primary font, and use preconnect for third-party origins you truly need, such as your analytics or video host. Keep the list short. Preloading five things means none of them is a priority.

10. Verify with real measurements

Test, do not assume:

  • Use curl -I on an HTML page and an asset; confirm the Cache-Control, ETag and cache-status headers match your intent.
  • Run a test from a distant location with a tool such as WebPageTest and compare TTFB before and after.
  • Watch field data for LCP and TTFB in the Core Web Vitals report over the following weeks. Lab gains that never appear in field data usually mean a cache is being bypassed for real traffic.

Quick checklist

  • Marketing site and product app on separate paths or hosts.
  • CDN serving HTML from the edge; second request shows HIT.
  • Hashed static assets cached for a year with immutable.
  • HTML on short browser cache with edge caching, plus purge on deploy.
  • No cookies set on public marketing pages; tracking parameters ignored in the cache key.
  • Personal pages marked private, no-store; errors cached briefly.
  • Verified search crawlers allowed through bot protection.
  • TTFB and LCP checked in lab and field data after rollout.
