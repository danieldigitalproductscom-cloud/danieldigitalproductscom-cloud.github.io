IndexNow and Faster Indexing for New AI SaaS Pages

You ship a new feature page, a pricing change or a comparison post, and then you wait. Days later it still is not in search results, or the old version is still showing. For a young AI/SaaS site with little authority, discovery speed is a real constraint. There are two separate problems here: telling search engines a URL changed, and convincing them it is worth indexing. This guide covers both, honestly, including where IndexNow helps and where it does not.

1. What IndexNow is, and what it is not

IndexNow is an open protocol that lets you notify participating search engines the moment a URL is added, updated or deleted. Bing, Yandex, Naver and Seznam support it; submitting to one participating endpoint shares the notification with the others. Google does not support IndexNow. For Google you rely on sitemaps, internal links and Search Console. So IndexNow is worth doing if Bing visibility matters to you (it also feeds some AI assistants and search products that draw on Bing's index), but it is not a Google shortcut.

It is also a notification, not a guarantee. A submitted URL still has to pass quality checks to be indexed. Thin or duplicate pages stay out no matter how you ping.

2. Set up IndexNow in four steps

  1. Generate a key. Any string of 8 to 128 characters using letters, digits and dashes. A random UUID works.
  2. Host the key file. Create a text file at your site root, for example https://example.com/3f9a1c2e-your-key.txt, containing only the key. This proves you control the host.
  3. Submit URLs. Send an HTTP POST to https://api.indexnow.org/indexnow with a JSON body: 
    {
  "host": "example.com",
  "key": "3f9a1c2e-your-key",
  "keyLocation": "https://example.com/3f9a1c2e-your-key.txt",
  "urlList": [
    "https://example.com/features/auto-triage",
    "https://example.com/pricing"
  ]
}
    A single URL can also be submitted with a GET request. You can send up to 10,000 URLs per request.
  4. Check the response. 200 or 202 means received. 400 is a malformed request, 403 means the key could not be validated, 422 means the URLs do not belong to the host, and 429 means you are sending too much.

If you use Cloudflare, or a CMS or static-site plugin that offers IndexNow, enabling it there is simpler than writing your own script. Otherwise add the POST as a final step in your deploy pipeline, sending only URLs that actually changed.

3. Only submit what changed

Do not submit your whole sitemap on every deploy. Compare the new build against the previous one and send added, edited and removed URLs only. Repeated submission of unchanged pages is noise and can trigger rate limiting. Send removed pages too, so engines drop them quickly instead of rechecking dead URLs.

4. For Google: sitemaps with honest lastmod

Google reads sitemaps, and it uses lastmod only if it has proven reliable. Set lastmod to the date of the last meaningful content change, not the build date. If every page claims to have changed today, Google learns to ignore the field. Keep the sitemap limited to canonical, indexable, 200-status URLs, and reference it in robots.txt and Search Console.

5. Internal links do more than pings

The most dependable discovery signal is a crawlable link from a page that is already indexed and visited often. When you publish a new page, link to it the same day from your home page, a relevant hub page or the navigation where appropriate, and from two or three related articles. An orphan page, even in the sitemap, is treated as low priority. Use plain <a href> links; links that exist only after a client-side click handler may never be followed.

6. Use URL Inspection sparingly and wisely

In Search Console, URL Inspection shows whether a page is indexed, the last crawl date, and the canonical Google chose. For a high-value new page you can use Request Indexing. Treat it as a nudge for a handful of important URLs, not a bulk tool; quotas are limited and repeat requests do not speed anything up. If Inspection reports "Discovered, currently not indexed" or "Crawled, currently not indexed," the issue is usually quality or duplication, not discovery. Strengthen the page with unique content, a clear purpose and internal links rather than resubmitting.

7. Make sure the page is indexable first

Before any pinging, rule out self-inflicted blocks. A leftover noindex meta tag or X-Robots-Tag header from staging, a Disallow rule in robots.txt, a canonical pointing at another URL, or a redirect chain will all stop indexing. Fetch the live page and confirm a 200 status, a self-referencing canonical, and that the main content is in the initial HTML rather than injected late by JavaScript.

8. Do not use the Indexing API for ordinary pages

Google's Indexing API is officially limited to job posting and livestream structured data. Using it for marketing pages is unsupported, and automated tools that promise instant indexing this way are not a dependable strategy. Stick to the supported methods above.

9. Measure time to index

Track how long new pages take to appear. For each new URL, record the publish date, the date it first shows as indexed in Search Console (and in Bing Webmaster Tools), and the date of first impressions. After a month you will see your typical lag, and you can tell whether a change such as adding hub links or IndexNow shortened it. This is far more useful than guessing.

Quick checklist

  • IndexNow key generated, key file live at the site root, POST wired into the deploy step.
  • Only added, changed and removed URLs submitted, not the whole site.
  • Expectations set: IndexNow covers Bing and others, not Google.
  • Sitemap lists canonical 200 URLs with a truthful lastmod.
  • Every new page linked from at least one indexed hub page and a few related articles.
  • No stray noindex, robots block, or conflicting canonical on the live page.
  • Request Indexing used only for key pages; time to index tracked per URL.
