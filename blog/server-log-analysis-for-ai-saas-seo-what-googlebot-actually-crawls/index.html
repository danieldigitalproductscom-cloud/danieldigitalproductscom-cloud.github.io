Server Log Analysis for AI SaaS SEO: What Googlebot Actually Crawls on Your Site

Most SaaS marketing sites are small enough that crawl budget is not a daily worry. But log files still answer questions no other tool can: Is Google fetching your new pricing page? Are crawlers burning requests on parameter URLs? Which pages return errors only bots see? Search Console reports sampled, delayed data. Your server or CDN logs record every request. This guide shows a lightweight way to use them.

Get the logs you need

You need, per request: timestamp, URL path with query string, status code, user agent, IP address, response time, and bytes sent. Where to find them depends on your setup:

  • CDN or host (Cloudflare, Vercel, Netlify, Fastly): enable log export or log push to storage. Many platforms keep only a few days by default, so turn on retention of at least 30 days.
  • Your own servers (nginx, Apache): access logs already contain these fields in the combined format; add $request_time if it is missing.
  • Privacy: logs contain IP addresses. Filter to bot traffic before sharing, and follow your retention policy.

Verify that "Googlebot" is really Googlebot

User agent strings are trivially faked, and a large share of requests claiming to be Googlebot are scrapers. Verify by reverse DNS: the IP should resolve to a hostname ending in googlebot.com or google.com, and that hostname should resolve back to the same IP. Google also publishes its crawler IP ranges as JSON, which is easier to match in bulk. Do the same for Bingbot using Microsoft's published ranges. Drop unverified requests from your analysis, otherwise your crawl counts will be inflated.

Questions to answer each week

  1. What status codes do bots receive? Group verified Googlebot requests by status. A healthy site is mostly 200 with a small share of 301 and 304. Many 404s, 5xx errors, or redirect chains deserve investigation.
  2. Which directories get the most crawling? If /app/, /api/, or search result pages receive more requests than /blog/ and /pricing, you are spending crawler attention on pages that cannot rank.
  3. Are important pages crawled at all? Compare your sitemap URLs against URLs Googlebot requested in the last 30 days. Pages never fetched are either not discovered (weak internal linking) or deprioritized (low perceived value).
  4. How often are key pages recrawled? Pricing, product, and comparison pages should be revisited within days. Weeks between visits suggest a weak signal of freshness or importance.
  5. How slow are responses to bots? Consistently slow time-to-first-byte reduces how much Google is willing to fetch. Watch the 95th percentile, not the average.

Common findings and fixes

  • Parameter sprawl. URLs like ?utm_source=, ?ref=, ?sort= crawled thousands of times. Fix with canonical tags, remove parameters from internal links, and block truly useless patterns in robots.txt.
  • Redirect chains. A request that goes http to https to www to a trailing-slash variant wastes four fetches. Point internal links and the sitemap at the final URL and collapse redirects into one hop.
  • Soft 404s and empty templates. Pages returning 200 with almost no content. Return a real 404 or 410, or add substance.
  • Stale URLs from old launches. Bots keep requesting removed pages for months. Redirect those with a relevant replacement, and let the rest return 410.
  • JavaScript and API endpoints. If crawlers hit JSON endpoints your pages depend on, confirm they are not blocked by robots.txt, since blocked resources can prevent correct rendering.
  • Authentication walls. Bots repeatedly receiving 302 redirects to a login page indicate internal links pointing into the app. Move those links behind a logged-in check or add rel="nofollow" where appropriate.

See which AI crawlers visit

Logs are also the only reliable way to see AI-related crawlers. Search for user agents such as GPTBot, ClaudeBot, PerplexityBot, and Google-Extended related fetches, and Applebot-Extended, then compare against your robots.txt policy. Check that the bots you allowed can reach your docs and product pages, and that the ones you disallowed are honoring it. Not every crawler respects robots.txt; if one does not, block it at the CDN or firewall using verified IP ranges. Decide your policy deliberately: allowing retrieval crawlers can help your product appear in AI answers, while blocking training crawlers is a separate choice.

A minimal workflow without special software

You do not need an enterprise log analyzer. A practical setup for a small team:

  1. Export 30 days of logs to a bucket or local folder.
  2. Load them into a database, a spreadsheet for small volumes, or a command-line tool such as DuckDB, which queries compressed files directly.
  3. Filter to verified search bots and group by path, status, and day.
  4. Save the queries so the same report runs every week; compare against the previous week rather than reading raw numbers.
  5. Log each fix with a date so you can see the effect on crawl patterns and indexing in Search Console two to four weeks later.

Cross-check with Search Console

Use the Crawl Stats report for the trend and logs for the detail. If Crawl Stats shows a drop in requests, logs tell you which sections stopped being fetched. If Page Indexing shows "Discovered, currently not indexed," check the logs: if Googlebot never requested those URLs, the problem is discovery and internal links; if it requested them and chose not to index, the problem is content quality or duplication.

Checklist

  1. Retain at least 30 days of logs with path, status, user agent, IP, and response time.
  2. Verify Googlebot and Bingbot by reverse DNS or published IP ranges.
  3. Review status code mix, top crawled directories, and uncrawled sitemap URLs weekly.
  4. Remove parameter URLs, redirect chains, and soft 404s from internal links and sitemaps.
  5. Check AI crawler activity against your robots.txt policy.
  6. Record each change and recheck the logs after a few weeks.
