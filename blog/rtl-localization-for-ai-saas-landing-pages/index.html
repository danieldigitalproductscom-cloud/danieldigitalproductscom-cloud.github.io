Designing AI SaaS Landing Pages for RTL Languages: The CSS Mistakes That Break Arabic and Hebrew Sites

Founders who localize into Arabic or Hebrew for the first time almost always ship the same bug: they translate the copy, add dir="rtl" to the <html> tag, and call it done. The page technically mirrors, but it still reads as a translated English page wearing a costume — icons pointing the wrong way, numbers reversed, form fields misaligned. Buyers in these markets notice immediately, and "this was clearly an afterthought" is not the impression you want on a page that's supposed to build trust. Here's what actually goes into a landing page that feels native in a right-to-left language, not just flipped.

1. Use logical CSS properties, not physical ones

margin-left, padding-right, and text-align: left don't know which direction the page is reading in — they'll happily apply the wrong spacing once dir="rtl" flips the layout around them, which is why so many "RTL-supported" pages still have a card with padding bunched on the wrong side. Replace them with logical equivalents: margin-inline-start, padding-inline-end, text-align: start. Written this way, the browser resolves "start" and "end" based on the page's actual direction, and the same stylesheet works for both LTR and RTL without a second, parallel set of overrides. If you're maintaining an existing English page, this refactor is the single highest-leverage change before attempting any RTL launch.

2. Mirror the layout, but not everything in it

Full mirroring is correct for navigation order, card layout, the direction a hero image "points," and the flow of a step-by-step process — a 1-2-3 how-it-works section should visually run right to left. But some things must not mirror: numerals stay left-to-right within themselves (١٢٣ or 123 reads left-to-right even inside RTL text), phone numbers and email addresses stay LTR, and universally recognized icons — a play button, a checkmark, a magnifying glass — should generally stay as-is rather than flip, since flipping them makes them harder to recognize, not more native. Directional icons are the real exception: an arrow pointing toward "next" or a chevron in a carousel should flip to point the way the page now reads.

3. Don't just flip icons that show real-world objects

A back-arrow icon should flip. A settings gear, a bell, a shopping cart, or a chat bubble should not — these represent physical objects, and physical objects don't reverse handedness just because the page direction changed. The practical rule: if the icon encodes a direction (arrow, chevron, "forward/back" affordance), mirror it. If the icon represents a thing, leave it alone. Getting this backwards is a small detail, but it's exactly the kind of small detail a native reader clocks in the first two seconds.

4. Pick a typeface that was actually designed for the script

Arabic and Hebrew have different letterforms, connecting-letter behavior (Arabic letters change shape based on position in a word), and vertical rhythm than Latin scripts, and a Latin webfont stack with a generic fallback renders Arabic in whatever ugly system font the browser defaults to — usually with cramped line-height and awkward letter joins. Use a webfont explicitly designed and hinted for the script (Google Fonts has solid Arabic and Hebrew families like Noto Sans Arabic, Noto Sans Hebrew, Cairo, Rubik), and increase line-height beyond your Latin default — Arabic in particular needs more vertical breathing room because of ascenders, descenders, and diacritics that Latin type doesn't have. Testing your English line-height value against Arabic copy is one of the fastest ways to spot a page that wasn't built for the language.

5. Handle bidi text — mixed RTL copy with embedded English or numbers

Real Arabic and Hebrew marketing copy is rarely pure single-direction text: a sentence mentioning "Slack" or "API" or a price like "$49/month" mixes an RTL sentence with LTR tokens embedded inside it, and the browser's bidirectional (bidi) algorithm doesn't always guess the intended order correctly, especially around punctuation and parentheses. When you see a phrase render with words in a visibly wrong order, wrap the embedded LTR token in a <span dir="ltr"> (or use the Unicode isolate characters) rather than trying to fix it by reordering the source text — reordering the text usually breaks it worse the next time a translator edits that string.

6. Forms: label position, input alignment, and placeholder text all need to flip together

A form is one of the easiest places for an RTL page to visibly break, because labels, inputs, icons-inside-inputs (like a search icon), and validation messages all need to move together. A search box with a magnifying-glass icon pinned to the physical left edge via left: 12px will end up on the wrong side of an RTL input — use inset-inline-start instead. Test every form on the page (email capture, contact, pricing calculator) specifically in RTL mode; forms get missed far more often than hero sections because they're usually built and QA'd last.

7. Don't mirror your product screenshots

If your landing page shows a screenshot or mock of the actual product UI, don't flip the image itself just because the surrounding page is RTL — unless the product UI is itself genuinely localized and mirrored (rare, and usually not worth building just for a landing page). A flipped screenshot of an English, LTR product looks obviously wrong to anyone who's used software before, because window chrome, buttons, and text inside the image will read backwards. Keep product screenshots as they naturally are and let the surrounding page layout do the direction work.

8. Test with a native reader, not just a translation checker

Automated RTL linters catch missing dir attributes and obvious CSS direction bugs, but they can't tell you that a headline reads stiffly, that a idiom translated literally sounds odd, or that a color or icon carries an unintended connotation in the target market. Before launch, have a native speaker actually use the page — fill out the form, read the pricing table, scan the FAQ — and treat their "this feels off" as seriously as a functional bug report, because for a localized page, "feels off" often is the bug.

The shortcut

Building RTL support into a page after the fact means auditing every physical CSS property, every icon, and every form on a page that was never structured for it — which is why it's dramatically easier to start from a template built with logical properties and a direction-aware layout system from day one, so flipping to Arabic or Hebrew is a configuration change instead of a rebuild.
